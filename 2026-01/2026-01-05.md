# 클라이언트와 서버


# 1. 클라이언트와 서버 정의

- 네트워크의 기본은 '요청'과 '응답'의 관계

| **구분** | **의미** | **비유 (식당)** | **역할** |
| --- | --- | --- | --- |
| **클라이언트 (Client)** | 서비스를 요청하는 쪽 | **손님** | 요청 생성, 응답 렌더링 |
| **서버 (Server)** | 서비스를 제공하는 쪽 | **직원** | 요청 처리, 리소스 응답 |

---

# 2. 클라이언트-서버 모델의 핵심 개념

- **클라이언트 (Client)**: 서비스를 **요청(Request)**하는 손님 (예: 웹 브라우저).
- **서버 (Server)**: 요청을 받아 서비스를 **응답(Response)**하는 주인 (예: 웹 서버).
- **프로토콜 (Protocol)**: 클라이언트와 서버가 서로 대화하기 위한 **공통 언어/규칙** (예: HTTP, TCP/IP).
- **IP 주소 (IP Address)**: 네트워크 상에서 서버가 있는 **위치/주소**.
- **포트 (Port):** 서버 내 특정 프로그램으로 들어가는 **문 번호**.
- **요청(Request) & 응답(Response):**
    - **헤더 (Header):** 보낼 데이터의 정보 (누구에게, 어떤 타입인지 등).
    - **바디 (Body):** 실제 전송하는 알맹이 데이터 (HTML, JSON, 이미지 등).

---

# 3. 통신의 흐름: 요청(Request)과 응답(Response)

데이터는 '택배'와 같은 구조로 전달되며, 크게 **헤더**와 **바디**로 나뉩니다.

| **구분** | **요청 (Request)** | **응답 (Response)** |
| --- | --- | --- |
| **비유** | "주문서" | "배송품" |
| **헤더 (Header)** | 목적지(Host), 원하는 방식(Method) 등 | 상태 코드(Status Code), 데이터 형식 등 |
| **바디 (Body)** | 추가 정보 (로그인 ID/PW 등) | 실제 데이터 (HTML, JSON, 이미지 등) |

### **상세 동작 단계**

1. **요청:** 클라이언트가 서버에 데이터 요청 (예: "내 프로필 보여줘").
2. **처리:** 서버가 요청을 분석하고 DB 조회 및 로직을 실행.
3. **응답:** 처리된 결과(HTML, JSON 등)를 클라이언트에 전송.
4. **렌더링:** 클라이언트(브라우저)가 받은 데이터를 화면에 시각적으로 표시.

# 4. 3계층 아키텍처 (3-Tier Architecture)

현대 웹은 유지보수와 확장을 위해 기능을 세 부분으로 분리합니다.

⇒ 과거의 '모놀리식(하나의 거대한 덩어리)' 구조의 한계를 극복하기 위해 역할을 세 부분으로 나눈 설계 방식

- **1계층: 프레젠테이션 (Presentation Tier)**
    - **역할:** 사용자 인터페이스(UI) 담당. 사용자와 직접 소통합니다. (예: 웹 브라우저)
- **2계층: 애플리케이션 (Application Tier)**
    - **역할:** 비즈니스 로직 처리. 데이터를 가공하고 인증을 수행합니다. (예: Spring, FastAPI)
- **3계층: 데이터 (Data Tier)**
    - **역할:** 데이터의 영구적 저장 및 관리. (예: MySQL, MongoDB)

### 3계층 아케텍처 표 정리

| **계층** | **이름** | **주요 역할** | **구성 예시** |
| --- | --- | --- | --- |
| **1계층** | **프레젠테이션** | 사용자 인터페이스(UI) 제공 | 브라우저, 모바일 앱 |
| **2계층** | **애플리케이션** | 비즈니스 로직 처리 (연산, 인증) | Spring Boot, FastAPI, Node.js |
| **3계층** | **데이터** | 데이터 저장 및 관리 | MySQL, MongoDB |

> 왜 계층을 나누나요?
> 
> - 각 계층이 독립적이므로, 사용자가 갑자기 늘어날 때 애플리케이션 서버만 증설하는 식으로 효율적인 확장이 가능하기 때문입니다.
> - 코드가 섞이지 않아 유지보수가 훨씬 쉽기 때문입니다.

# 5. 클라이언트-서버 모델 장단점 및 핵심 용어

### **장단점 비교**

- **장점:** 데이터 중앙 집중 관리로 보안 향상, 서버 업데이트 시 모든 사용자에게 즉시 반영.
- **단점:** 서버 과부하 가능성, 서버 고장 시 전체 서비스 마비.

### **핵심 용어 정복**

- **SPOF (단일 장애점):** 시스템 구성 요소 중 하나만 고장 나도 전체가 멈추는 지점. 이를 막기 위해 서버를 여러 대 두는 **이중화**가 필요
- **프로비저닝 (Provisioning):** 사용자의 요구에 맞게 자원(서버, 메모리 등)을 준비해두는 과정.
- **과대 프로비저닝 (Over-provisioning):** 갑작스러운 트래픽 폭주에 대비해 실제 필요한 것보다 **더 많은 자원을 미리 확보**해두는 전략

# 6. DNS (Domain Name System)

우리는 웹사이트에 접속할 때 `naver.com` 같은 이름을 쓰지만, 컴퓨터는 숫자로 된 **IP 주소**(`223.130.195.200`)만 이해합니다.

- **정의:** 도메인 이름을 IP 주소로 변환해 주는 서비스입니다.
- **동작 과정:**
    1. 사용자가 브라우저에 `google.com` 입력.
    2. 브라우저가 **DNS 서버**에 https://www.google.com의 IP 주소가 뭐야? 라고 질문.
    3. DNS 서버가 실제 주소(`142.250.196.110`)를 응답.
    4. 브라우저는 해당 IP 주소를 가진 서버로 **HTTP 요청**을 보냄.

# 7. 대화의 목적을 명시하는 HTTP 메소드와 CRUD

클라이언트가 서버에 요청을 보낼 때, 단순히 "연결해줘"가 아니라 **"무엇을 할 것인지"** 목적을 밝혀야 합니다. 이를 **CRUD** 개념과 매칭합니다.

| **작업 (CRUD)** | **의미** | **HTTP 메소드** | **실제 사례 (게시판)** |
| --- | --- | --- | --- |
| **C**reate | 생성 | **POST** | 새로운 게시글 등록하기 |
| **R**ead | 조회 | **GET** | 게시글 목록이나 내용 읽기 |
| **U**pdate | 수정 | **PUT / PATCH** | 작성한 글 내용 수정하기 |
| **D**elete | 삭제 | **DELETE** | 게시글 삭제하기 |
- **GET:** 데이터를 가져올 때 사용. 주소창에 데이터가 노출되므로 보안에 취약하지만 속도가 빠름.
- **POST:** 데이터를 생성할 때 사용. 메시지 **Body**에 데이터를 숨겨서 보내므로 대용량이나 민감한 정보 전송에 적합.

# 8. 서버의 대답: HTTP 상태 코드 (Status Code)

서버는 응답 시 처리 결과를 세 자리 숫자로 알려줍니다. 이 숫자를 보면 무엇이 문제인지 바로 알 수 있습니다.

- **200 OK:** 요청이 성공적으로 처리됨.
- **201 Created:** (POST 요청 시) 새로운 리소스가 성공적으로 생성됨.
    - 200번대 → 성공

- **400 Bad Request:** 클라이언트가 요청을 잘못 보냄 (문법 오류 등).
- **401 Unauthorized:** 권한이 없음 (로그인 필요).
- **404 Not Found:** 요청한 페이지나 데이터를 찾을 수 없음.
    - 400번대 → 클라이언트 쪽 문제

- **500 Internal Server Error:** 서버 내부 로직 오류 (서버 개발자의 실수).
    - 500번대 → 서버 쪽 문제

⇒ 2xx - 성공 응답

⇒ 3xx - 리다이렉션

⇒ 4xx - 클라이언트 오류

⇒ 5xx - 서버 오류

# **9. HTTP 메시지의 상세 구조**

HTTP는 텍스트 기반의 프로토콜로, 클라이언트가 보내는 요청(Request)과 서버가 보내는 응답(Response)의 구조가 정해져 있습니다.

---

### **1. Header (헤더): 데이터의 머리**

- **역할:** Body(본문)를 열어보기 전에 필요한 정보(메타데이터)를 미리 알려줍니다.
- **형식:** `이름: 값` (예: `Content-Type: application/json`)

### **주요 Header 종류**

- **요청(Request):**
    - `Host`: 받을 서버 주소 (받는 사람)
    - `User-Agent`: 내 브라우저/앱 정보 (보내는 사람 신분)
    - `Authorization`: 인증 토큰 (출입증)
- **응답(Response):**
    - `Content-Type`: 데이터의 형식 ("이건 한글/사진 입니다")
    - `Content-Length`: 데이터 크기 (무게/장수)
    - `Set-Cookie`: 상태 저장 정보 ("다음에 올 때 보여주세요")

---

### **2. Body (바디): 데이터의 몸통**

- **역할:** 실제 주고받는 **핵심 내용물**
- **특징:**
    - **GET(조회)** 요청에는 보통 **없음**.
    - **POST(전송)** 요청이나 **성공한 응답**에는 **있음**.

### **데이터 형식 (Content-Type)**

Body에 담긴 데이터가 무엇인지는 Header의 `Content-Type`이 결정합니다.

- `text/html`: 웹페이지 (HTML 문서)
- `application/json`: 데이터 통신용 (JSON)
- `multipart/form-data`: 파일 업로드
- 

| **구조** | **설명** | **택배/편지 비유** |
| --- | --- | --- |
| **1. Start Line** | 무엇을 할지(요청) 또는 결과가 뭔지(응답) 적는 첫 줄 | **봉투 겉면** (받는 사람 + 용건) |
| **2. Header** | 본문보다 먼저 확인하는 부가 정보 (데이터의 성격, 크기 등) | **송장/스티커** (보내는 사람, 배송 옵션) |
| **3. Empty Line** | Header와 Body를 나누는 구분선 | (봉투 안과 밖의 경계) |
| **4. Body** | 실제로 전달하려는 핵심 데이터 (상황에 따라 없을 수도 있음) | **내용물** (편지 내용, 실제 물건) |

# **10. HTTP 메소드 (행위의 정의) = 동작**

클라이언트는 서버에 요청을 보낼 때 '어떤 종류의 작업'을 원하는지 메소드를 통해 명시합니다. 

| **CRUD** | **HTTP Method** | **의미** | **식당 비유** |
| --- | --- | --- | --- |
| Create | POST | 새로운 데이터 생성 | 새 메뉴 주문하기 |
| Read | GET | 데이터 조회 | 메뉴판 보기 |
| Update | PUT / PATCH | 데이터 수정 | 주문 변경하기 |
| Delete | DELETE | 데이터 삭제 | 주문 취소하기 |

### PUT vs PATCH 비교

| **구분** | **PUT** | **PATCH** |
| --- | --- | --- |
| 수정 범위 | 전체 교체 | 부분 수정 |
| 보내야 할 데이터 | 모든 필드 | 변경할 필드만 |
| 비유 | 책 전체를 새로 인쇄 | 오탈자만 수정 |

### 2. 무상태성 (Stateless)
